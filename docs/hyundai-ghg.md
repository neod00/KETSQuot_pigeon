# 현대차 협력사 GHG검증

## 화면

- `/hyundai-ghg/admin`: 내부 로그인 후 사용하는 통합 관리 화면. 대시보드와 공통 왼쪽 메뉴에서 접근한다.
- `/hyundai-ghg/existing`: LRQA 검증 이력이 있는 업체의 간편 신청서.
- `/hyundai-ghg/new`: 기존 `/p827`과 동일한 전체 P827 신청서. 조직·재무·운영·지역 경계, 사업장, 공정, 검증기준, 온실가스, 보고기간, 보증수준, 중요성 등 원본 폼의 모든 항목을 사용한다.

신청 링크는 유형별 공통 링크이며, 관리 화면의 링크 복사 버튼으로 안내한다. 고객은 포털 로그인 없이 작성할 수 있다. 회사별 초대 토큰과 전년도 실적·견적 불러오기는 사용하지 않는다.

고객용 두 링크는 별도 화면으로 제공하며 신청서 안에서 유형을 전환하지 않는다. 신규 신청서는 원본 P827과 동일한 화면 구성·입력 동작·필수 항목을 공유하고, 접수처만 현대차 협력사 전용 API로 구분한다. 기존 `/p827`은 원래 P827 접수함에 그대로 저장한다.

기존 고객용 검증대상년도는 드롭다운에서 연도를 추가하고 선택한 연도 태그에서 개별 해제한다. `targetYears`에 선택한 전체 연도를 보관하고 목록·상세·연도 필터에 반영한다. 이전 접수의 단일 `targetYear`도 계속 읽을 수 있다. 문서에 신청정보를 반영하면 선택한 연도를 모두 옮기며, 연속되지 않은 연도는 각각의 기간으로 명시한다. 검증일수와 금액은 연도 수로 자동 배수 계산하지 않는다.

신규 신청의 전체 P827 입력값은 `p827Application`에 보관하고 내부 신청내용·제출 원본 화면에서도 같은 폼으로 열람·수정한다. 목록의 회사명, 대상년도, Scope 등은 전체 입력값에서 요약한다. P827 원본에서 선택 입력인 주소·사업장·보고기간은 신규 신청에서도 선택 입력이며, 보고기간이 없으면 목록에 대상년도 미입력으로 표시한다. 기존 간략 신규 양식으로 받은 이전 접수 건은 계속 열람할 수 있다.

## 관리 흐름

1. 목록에서 업체를 선택하고 신청내용을 확인하거나 수정한다.
2. 내부 검토 탭에 메모를 입력하고 처리상태를 변경한다.
3. 견적·계약 탭에서 주소·대표자·검증조건·검증일수·금액을 직접 보완한다. 현재 신청내용을 다시 옮길 때는 **현재 신청정보를 문서에 반영**을 누른다. 대표자명은 고객 담당자명으로 자동 채우지 않는다.
4. **변경사항 저장**으로 신청내용, 상태, 메모와 견적 조건을 함께 보관한다.
5. 같은 탭에서 기존 P827 템플릿을 이용해 견적서 및 계약서 Word 다운로드/PDF 인쇄를 실행한다. 검증일수·금액이 없으면 생성을 차단한다.

상태는 접수 → 검토 중 → 보완 요청 → 견적 생성 → 계약 완료를 사용한다. 상태 선택과 문서 생성은 별개이며 담당자가 상태를 관리한다. 링크나 보완 요청을 이메일로 자동 발송하지 않는다.

고객 제출 원본은 수정하지 않으며 처리이력 탭에서 열람한다. 수정자와 처리상태 변경을 기록하고, 같은 버전을 동시에 수정하면 나중 저장을 거절해 덮어쓰기를 막는다. 같은 회사명·대상년도의 신청은 경고하되 별도로 보관한다.

## 저장 및 권한

운영 환경은 기존 Netlify Blobs 컨텍스트를 사용하며 `hyundai-ghg-applications` 저장소에 보관한다. 기존 P827/CBAM 접수와 분리된다. 목록·개별 조회·수정 API는 내부 세션을 확인한다. 공개 POST는 신청 입력값만 받아들이며 접수번호와 접수시각만 반환한다.

개발 환경에서 Netlify 컨텍스트가 없으면 프로세스 메모리를 사용하므로 서버 재시작 시 테스트 신청서는 사라진다. 운영 모드에서는 저장소 설정이 없을 경우 저장 실패를 반환하며 메모리에 접수하지 않는다.

## 검증

`web-app`에서 `node --import tsx --test tools/hyundai-ghg.test.ts`를 실행한다.

로컬 개발 서버에 대한 HTTP 통합 테스트는 `GHG_TEST_ORIGIN=http://127.0.0.1:<포트>`와 개발 서버의 `ISO_SESSION_SECRET`에 대응하는 `GHG_TEST_SECRET`을 테스트 프로세스에 설정한다. 테스트는 localhost만 허용하며 가상의 회사·연락처로 접수·조회·수정·원본보존·동시수정 충돌·접근권한을 확인한다. 운영 사이트에는 실행하지 않는다.

## 배포

프로젝트 루트에서 기존 Netlify 사이트에 연결해 `netlify build --context production`으로 함수·정적 파일을 함께 빌드한다. 빌드 명령은 검증한 Webpack 방식이다. Windows의 Netlify Node middleware 패키징 호환 문제를 피하기 위해 접근 제어는 `src/middleware.ts`의 Edge 실행 방식을 사용한다. 기존 HMAC 세션 검증과 공개 경로 조건은 유지하며 `tools/access-gate.test.ts`로 정상·변조·만료 세션을 검증한다. Next.js 16에서는 이 파일 명칭이 deprecated이지만 Edge 실행 용도로 지원된다. 향후 Proxy로 변경할 때는 배포 어댑터의 호환성도 함께 확인한다.

배포 주소에 대해 `node tools/verify-hyundai-deployment.mjs <배포 URL>`을 실행하면 고객 신청서, 원본 P827과의 일치, 로그인 보호, 필수값 오류, 문서 템플릿을 확인한다. 이 검증은 유효한 신청서를 제출하지 않으며 운영 데이터를 생성하지 않는다.

CLI 배포는 `web-app`을 작업 디렉터리로 삼아 빌드와 업로드를 한 번에 실행한다. 사이트에 설정된 원격 base가 다시 적용되지 않도록 이 실행 동안만 `web-app/netlify.toml`의 `[build]`에 `base = "."`을 추가하고 종료 시 원본을 복원한다. `netlify deploy --build --context production --site 0e8094dc-c1d1-4100-848e-f37af61c8388`으로 임시 배포한 뒤 확인한 배포 ID를 게시한다. 업로드 로그에 함수 캐시 사용 및 Edge 함수 포함을 확인한다. 별도 `--no-build` 업로드는 함수 캐시 만료, Edge 파일 누락, 정적 디렉터리 복원으로 실행 정보가 손실될 수 있으므로 피한다.

2026-10-27 운영 게시: `6ae0aefb87e1937a04909d88`. 운영 주소의 12개 경로·접근제어 검사와 P827 폼 일치 검사를 통과했다. 유효한 고객 신청서를 운영에 시험 제출하지 않았다. 직전 운영 배포 ID는 `6ac89f8b3cae0d0007296a08`이다.
